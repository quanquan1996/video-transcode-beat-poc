## 结论

1. **性价比最高：us-west-2 的 g6f.xlarge GPU 机群（1/8 块 L4，$0.2375/小时）。** 4K60 HDR 约 4.4 分钟出结果，每个视频 $0.017，3 台常驻每月约 $600（含节拍识别）。这是 us-west-1 最便宜方案的 **1/2.5**。
   - 限制：显存只有 3 GB，8K 只能跑 1 路，4K HDR 跑 2 路。它是 vGPU 时间片共享（显示为 L4-3Q），宿主机忙的时候性能可能有波动，上线前建议做 1–2 天的压测。
2. **最快：Lambda 切 16 片，1 分钟左右出结果**，每月 $1,300–2,300，不用管服务器，没有视频时不花钱。arm64 在 us-west-2 最便宜。适合消化高峰。
3. **推荐架构：GPU 常驻机群扛日常量 + Lambda 扛高峰。** 两条路线用同一份代码（同一个 worker）；分流逻辑（例如按队列长度把超出 GPU 机群能力的视频转给 Lambda）需要在生产化时补上，本仓库还没有实现。
4. **为什么要选 us-west-2：** us-west-1 只有 g4dn（T4），HDR 每月最低约 $1,460；us-west-2 有 g6、g6f、g5、g6e。GPU 方案便宜 60% 左右，Fargate 和 Lambda arm64 也便宜 18–26%。
5. **MediaConvert 这次不合适：** 4K60 HDR 要 6–7 分钟，8K 要 16–34 分钟，每个视频 $0.22–0.26，是最慢也最贵的。它的优势是全托管、免运维。
6. **节拍识别放 Fargate CPU：** 每个视频 $0.005，约 1.5 分钟，不需要 GPU。Lambda 上冷启动波动比较大。

## 还能再优化（来自实测）
- **HDR 的瓶颈在 CPU 色调映射**：同一块 T4，8K SDR 只要 1.9 分钟，4K HDR 却要 5.6 分钟。把色调映射搬到 GPU 上（ffmpeg 的 `tonemap_opencl` 或 libplacebo），HDR 预计能接近 SDR 的速度，GPU 机群可以再减 1–2 台。
- **GPU 机群用 Spot 或 Savings Plan**，还能再降 30–60%。
- **镜像瘦身**：把 GPU/Fargate 用的 ffmpeg 镜像和 torch 镜像拆开，可以缩短冷启动。
- NVENC 码率已经设了上限（目标 2.5 Mbps，最高 4 Mbps）。实测输出约 3.3 Mbps，x264 约 2.2 Mbps，可以按画质要求再调。

## 测试中遇到并已解决的问题
- MediaConvert 加速转码要求在作业级别设置 `TimecodeConfig.Source=ZEROBASED`，否则会自动退回普通模式。
- g6f.xlarge 显存 3 GB：4 路并行解码 4K 10-bit 会显存不足，现在每种机型可以单独设置并行路数。
- Lambda x86 镜像缺 `libgomp`（PyTorch CPU 版需要），已补上。
- g5.xlarge 和 g6.2xlarge 在 us-west-2a/2b 都遇到过暂时缺容量。生产环境建议多可用区，并给 ASG 配多种备选机型。

## 下一步建议确认的信息
- 源视频里 HDR / SDR、4K / 8K 的比例，以及每天的高峰时段（决定机群规模和 Lambda 分流的比例）
- 720p 的码率 / 画质要求，以及 HDR 是否一定要转成 SDR
- beats.json 怎么用（是否需要 BPM、强拍、置信度）
